# Agent 规则

> 提取自 Agent 工程和 Agentic Engineering 文章。定义多 Agent 协作的角色分工、流程交接和质量门禁。
> 优先级：**P0-P1** 硬约束和强推荐。

---

## P0：不能越界修改

**下游 Agent 不能改上游的输出，只能提阻塞项。**

- 开发 Agent 不能改需求文档
- 审查 Agent 不能改开发 Agent 的代码（只能提问题）
- 阻塞项通过 PM 打回上游修改，不直接动手
- 这叫「角色职责边界」，比「谁都能改」更安全

---

## P0：完成必须有验证

**开发前后各跑一次基线验证脚本，用增量说话。**

- 开发前：记下当前基线状态（编译? 测试?）
- 开发后：跑同样的脚本看增量
- 防止 AI 说「做完了」但实际上改了不该改的东西

---

## P1：单 Agent 角色冲突时拆角色

**当一个人既做需求又写代码又审查时，必须拆开。**

- 最少分工：需求 + 设计 + 开发 + 审查 + 测试
- 拆的时机：感觉「做不过来」或「自己审自己不合理」的时候
- 不追求一步到位，被问题逼到再拆

---

## P1：人的判断权高于 AI

**关键决策必须人拍板，AI 不能替人做判断。**

- 需求方向、技术方案选型、发布决策是人判断
- 代码怎么写、测试怎么跑、文档怎么写是 AI 执行
- 人在以下方面不可替代：
  1. 定义什么是正确的
  2. 看出哪里偏了
  3. 判断方向对不对

---

## P1：PM 只做路由不做专业判断

**PM Agent 的角色是路由器，不是专家。**

- PM 管：任务分配、流程推进、交接、回退
- PM 不管：技术判断、代码质量、设计决策
- PM 如果开始做专业判断，就是越界了

---

## P1：结构化调度优于自由讨论

**多 Agent 协作必须有明确的层级和流程，不能自由讨论。**

- 自由讨论式 → 路径不稳定、责任不清、难维护
- 结构化调度 → 流程清晰、可审计、可追溯
- 类比：有主持人（PM）的会议 vs 没主持人的七嘴八舌

---

## P2：不同角色配不同模型

**高推理需求角色用强模型，流程角色用便宜模型。**

- PM（路由、读文档）→ 便宜小模型
- 需求分析、方案设计、审查、测试 → 强模型
- 目的：省钱的同时，专业环节拿到更合适的能力

---

## P2：凭证不进沙盒

**所有密码/API Key 存在独立保险库，AI 不直接接触。**

- 凭证通过代理按需获取
- 最小权限（只给需要的）
- 可审计（所有外部调用有记录）
- 可统一轮换

---

## P2：PPAF 循环

**Agent 的工作方式是：感知→规划→行动→反思。**

- 不跳过规划直接行动
- 行动后必须反思（结果对不对？哪里可以改进？）
- 反思后把经验记录成 Rule/Skill（进化）

---

## P3：拆角色顺序由问题驱动

**不是一开始就拆 7 个 Agent，是先有基础三层（需求/方案/开发），被问题逼着一步步加的。**

拆的顺序：
```
基础三层（需求/方案/开发）
  → 发现没人把关 → 加闸门总控
  → 发现没人收口 → 加审查和测试
  → 发现流程串不起来 → 加 PM
```
