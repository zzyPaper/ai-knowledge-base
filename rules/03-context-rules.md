# 上下文规则

> 提取自 Context Engineering 文章。定义怎么给 AI 提供信息、信息怎么组织、知识怎么管理。
> 优先级：**P0-P2**

---

## P0：规则必须沉淀到仓库

**所有设计决策、编码规范、标准操作必须写到仓库里，AI 不靠记忆。**

- 设计决策 → SPEC 或 ADR（架构决策记录）
- 编码规范 → Rule 文件
- 标准操作 → Skill 文件
- **全部提交到仓库，版本化管理**

为什么：代码仓库是 AI 唯一能看到的世界。AI 看不到你脑子里的想法和口头约定。如果不沉淀，每次换人用 AI，同样的规矩要重新教。

---

## P1：先给目录，再给内容

**AGENTS.md 控制在约 100 行，只当索引。**

- 不把全部规则塞进一个文件
- 需要细节时再到对应文件里找
- SKILL.md 同理：先给摘要，详细内容按需加载

类比：新员工入职先给部门通讯录，不塞三本操作手册。

---

## P1：规则必须写得可验证

**所有业务规则要写到 AI 能写测试来判断的程度。**

- ❌ 差：「支付金额要合理」（AI 不知道什么叫合理）
- ✅ 好：「支付金额 > 0 且 ≤ 账户余额，超出返回 ERR_INSUFFICIENT_BALANCE」（AI 能写断言验证）

**详尽的用例不只是给 AI 更多信息——它提供了判断标准。**

---

## P2：渐进式披露

**先给最相关的摘要，需要时再展开。**

- 不一次性把所有相关代码都塞给 AI
- 先给核心文件的接口和关键逻辑 → 需要细节再读完整文件
- Token 分配：核心代码 40% > 规则 20% > Skill 20% > 历史 10% > 其他 10%

---

## P2：优先用 Grep 搜索代码，不用预建索引

**代码搜索用精确匹配，不用语义搜索。**

- 搜索标识符（类名、方法名、变量名）→ Grep 精确匹配最直接
- 搜索自然语言描述 → 可以先用 Grep 缩小范围，或用 embedding 补充
- 不建向量索引，不预埋 embedding

原因：代码 95% 关键词是标识符，精确匹配天然合适。ripgrep 扫描 4500 文件只需 0.1 秒。

---

## P2：分层记忆

| 层级 | 内容 | 生命周期 |
|------|------|---------|
| 短期 | 当前对话上下文 | 本次会话 |
| 长期 | 持久化的 Rule/Skill/Memory | 跨会话 |

- 重要信息要写入持久存储（Memory 文件），不能只依赖对话记忆
- AI 自己要会主动写笔记（通过记忆工具）

---

## P2：仓库资产是权威来源

**同一条信息，仓库里的版本优先于 Memory 里的版本。**

- 不同人的 Memory 可能自相矛盾
- 仓库资产经过 PR 和 Review，更可靠
- Memory 适用于个人偏好和临时信息，不适用于团队共识
- 定了的结论 → SPEC/看板/dev-map；反复踩的坑 → Scripts/Rule

> 真正专业的 Harness 应该是：任何人拿到这个工程，都能顺着这套系统做对事情。

---

## P3：Token 流水线意识

**理解 AI 每次处理任务的 Token 消耗过程：**

```
收集 → 排序 → 压缩 → 预算 → 组装
```

- 不浪费 Token 在无关信息上
- 长内容优先压缩，保留接口和核心逻辑
- 按优先级给不同类别分配 Token 限额
